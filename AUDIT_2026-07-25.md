## 1. The reported bug: chapters appearing late / inconsistent timestamps

> "our updates found it 1 hour ago, but the series page says the chapter was updated in the source site 1 day ago"

This was **two independent bugs**. The display bug was honestly reporting the discovery bug.

### 1a. Discovery lag — measured p50 ≈ 29 hours

`resolve_interval` set each series' **poll cadence equal to its own average publication gap**, clamped to `[6h, 336h]`. Polling at the publication rate guarantees an average detection lag on the order of the interval.

Measured against Suwayomi's `fetchedAt − uploadDate` (n=271 genuine incremental additions): **p25 3.2h, p50 28.8h, p75 6.7d, p90 11.4d**, and the lag tracked the scan interval monotonically. 51% of ONGOING series (3,189 of 6,255) were scheduled **more than 7 days apart**. Coverage: 77% of the library went >72h between scans while ~1,700 hot series consumed the budget.

Contributing causes, all confirmed:

- **4,335 legacy rows parked years in the future** — written under an old ~100-year ceiling, `MAX(next_scan_at) = 2033-03-14`. Permanently invisible to the due-query. 1,648 were ONGOING.
- **`awaiting_since` was never reset**, so a series that once de-accelerated could never re-accelerate. 1,676 of 2,202 awaiting series (76%) were permanently stuck on a 7–14 day poll — "poll hard for 2 days, then go blind for 2 weeks".
- **`awaiting` was true by construction** (`due_now` is always true for scheduler-driven scans), so it meant "a scheduled scan found nothing", the normal case. 386 series consumed ~77% of all scan capacity.
- **One `Utc::now()` per tick** applied to a batch of up to 5,000, so a backlog wrote `next_scan_at` values already in the past and never converged.

**Fixed** by separating three concepts that had been one number: _publication interval_ (judges lateness only), _steady poll interval_ (`clamp(publication, 6h, 12h)`), and _park_ (14d, paused only). Lateness is now measured against upstream's own clock, inside a band `(1.25×, 3.0×]`, so a series that simply stopped publishing doesn't accelerate forever. `DUE_BATCH_LIMIT` 5000→1000.

Throughput: projected **~20,560 scans/day** vs **30,119/day actual today** and ~295/tick demonstrated capacity — a **32% reduction** in upstream fetches while cutting the worst-case cadence from 336h to 12h. **Projected median lag ~29h → ~6h**, p90 from 11.4d to ~12h.

### 1b. Three clocks rendered under one label

| Surface                      | Field rendered | Actual meaning       |
| ---------------------------- | -------------- | -------------------- |
| Updates grid — Suwayomi rows | `updatedAt`    | our detection time   |
| Updates grid — MangaDex rows | `latestAt`     | real publish time    |
| Series page header           | `updatedAt`    | our detection time   |
| Series page chapter rows     | `uploadedAt`   | upstream upload date |
| Browse / Trending cards      | `updatedAt`    | our last poll time   |

The server documents `updated_at` as unusable for this (`types.rs:143-145`: _"Do NOT use as 'recently updated' — it moves on every poll"_) and exposes `latest_chapter_at` as the correct field. It was added to the GraphQL schema but **`SERIES_FIELDS` never selected it**, so it never reached the client. The `updates` resolver additionally _overwrote_ `updated_at` with detection time.

**Fixed**: resolver stops overwriting; new `detectedAt` field added; client selects `latestChapterAt` and `detectedAt`; release time is the label, detection time the tooltip. `relTime`/`relTimeAgo` unified (a 2-year-old chapter no longer renders "730d").

Verified: **SSR of `/series/1271` now renders `Updated 7d`**, where raw `updatedAt` is "0h".

### 1c. Also found — the sharpest version of the complaint

`resolve_chapters_cached` (90-min TTL) live-fetches on a reader request and calls `put_chapters`, but **does not** update `series_scan_state`. So a chapter becomes readable immediately, the feed doesn't learn of it until the next scheduled scan, and then announces as "just now" a chapter readable for days. _Identified, not yet fixed — see Outstanding._

## 2. Critical: the next restart would have destroyed 11,580 works

`maintenance_flag` is empty because the one-time catalogue backfill failed, so **any** container restart re-ran it; on success it called `run_post_ingest_dedup`, which looped `consolidate_exact_duplicate_works` **until the whole catalogue was folded**.

That consolidator merged any works sharing _one normalized alias_ — and MangaDex alt-titles give distinct series identical aliases. Verified against live data:

```
clusters_total  works_merged  clusters_of_2
9464            11580         8167
```

- `ジョジョの奇妙な冒険` → **10 works**: Phantom Blood (1986), Battle Tendency (1987), Stardust Crusaders (1989), Stone Ocean (2000), JoJolion…
- `dragon ball` → includes _Jaco the Galactic Patrolman_, a different manga
- `first love` → 18 distinct works
- **3,371 clusters** contain works whose `year` differs by >1

`merge_works` physically DELETEs the loser — no `merged_into` pointer, no undo. Chapter loss compounded it: `select_reader_chapters` keys on chapter _number_, and the JoJo cluster has 1,190 chapters but only 158 distinct numbers — **~87% would become unreachable**.

**Fixed** with a conservative gate: shared alias must be the primary title of _both_ works, cluster size exactly 2, title ≥5 chars, plus corroboration (year ±1, or matching author, or pHash ≥0.90). Refusals route to the review queue.

```
would_merge_under_new_rule: 1157   (from 11,580)
```

All three examples above are refused on cluster size alone. Corroboration breakdown of the 2,085 eligible pairs: year 172, author 1,086, **pHash 0** — only 31 pairs even have both hashes, confirming pHash could never have been the sole gate.

Related fixes: the exact-title auto-merge rung in `dedup.rs` bypassed the ambiguity guard the federated path already had (1,624 works carry a colliding sub-5-char title; `COVER_PHASH=off` in production so cover corroboration could never fire). `merge_works` was also lossy — it discarded descriptions, credits, cover galleries and admin overrides, didn't fold `is_nsfw` (so merging NSFW into SFW served it to anonymous viewers), and left `canonical_library`/`work_cover_issue` dangling. All folded now, and a `work_redirect` table means merged-away ids resolve instead of 404ing.

## 3. Security

The **application code was clean**. All 47 mutations and 35 queries were enumerated: every admin operation has `require_admin`, no resolver accepts a client-supplied user id (**no IDOR**), Argon2id with per-password salts, opaque 256-bit session tokens (no JWT, no signing secret), no path traversal (everything is SQLite BLOBs — there are no filesystem writes), no SSRF primitive, uploads capped pre-decode and re-encoded to WebP (so SVG/HTML stored-XSS is impossible), no `@html` anywhere in either frontend, no secrets committed to git.

Findings were all in the deployment layer:

## 4. Content gating

The effective NSFW flag is `COALESCE(is_nsfw_override, is_nsfw)`, but four SQL page filters tested raw `is_nsfw` — and **both** admin "mark NSFW" mutations write _only_ the override column, producing exactly the state those filters ignored. Verified live and anonymous: `search(query:"", page:17)` returned works with `isNsfw: true` while `canonicalSeries` on the same work correctly refused.

`workSources` had no work-level gate at all, leaking existence and MangaDex UUIDs for works the reader is barred from.

All fixed, with Rust-side `filter_nsfw` backstops added to `search` and `updates` to match what `discovery` already did.

Separately, an opted-out admin's console **silently omitted every NSFW-flagged work** — including the ~2,500 mainstream titles known to be wrongly flagged, i.e. exactly the set the console exists to fix. Fixed with an `includeNsfw` argument honoured **only** for admins (anonymous callers short-circuit before it's consulted), plus a `setShowNsfw` toggle the console previously had no way to reach.

## 6. Storage

**8,868 orphaned cover blobs ≈ 1.53 GB** had leaked from past merges and purges (the covers DB is a _separate_ database and nothing ever reclaimed it). Now swept hourly, batched and interruptible, with:

- a 24h minimum age re-evaluated **atomically inside the DELETE**, so a blob re-materialized between probe and delete survives
- a disaster guard: the sweep aborts unless `work` has ≥10,000 rows, so a restored-main-DB-with-surviving-covers scenario can't empty a 20 GB cache

Dry run against production identified 8,868 + 78 orphans, zero false positives, full pass in 0.45 s. Deleting does **not** shrink the 20.5 GB file (freelist reuse); growth stops, disk isn't returned. No `VACUUM` added deliberately.

## 7. Frontend

Reader: series pages were SSR-ing an **empty skeleton** (load returned an unawaited promise; effects don't run during SSR) and the edge cached it for 60s — defeating SEO and link previews entirely while still burning the backend fan-out. The `browser ? p : await p` streaming idiom was also wrong on hydration (universal loads always re-run in the browser), causing real cards to paint then blank to skeletons then refetch. Browse's federated opt-in was sticky across query edits, so every keystroke fanned out to 24 sources until the rate limiter tripped — which then showed the _old_ query's rows under the _new_ query's header. Optimistic library mutations could never roll back, because the data layer caught backend errors and returned the optimistic value.

Admin: "Consolidate duplicates" was a one-click, no-confirm, unbounded `for(;;)` over the whole catalogue — now confirmed, bounded and stoppable. Text-search results were rendered with actions that assume numeric Suwayomi ids, so `Add` was a guaranteed error, provenance showed a misleading "not catalogued", and `Merge…` silently vanished.

## Outstanding — not fixed

1. **Reader-triggered chapter refresh doesn't update `series_scan_state`** (§1c). The remaining piece of the reported bug: a chapter found by a reader request is announced by the feed as "just now" days later.
2. **`refresh_feed_updates` / `refresh_work_fts` rebuild wholesale** — 157k rows under `BEGIN IMMEDIATE` every 6h to reflect ~20 changed works. Measured a **48-second exclusive lock**, past the 15s `busy_timeout`; all 44 "database is locked" checkpoint errors cluster exactly there. Needs incremental rebuild or FTS5 triggers.
3. **`put_series` still rewrites every scan** — the remaining third of per-scan WAL. Needs the same memo treatment `put_chapters` got; skipping naively would break the 6h metadata-freshness gate.
4. **1,956 Suwayomi-only works with NULL `content_rating`** remain wrongly flagged NSFW. Migration 0053's WHERE clause structurally can't reach them (no authoritative MangaDex rating).
5. **`work_alias` UNIQUE doesn't constrain** — `lang` is NULL on 12,981 rows and NULLs are distinct in SQLite, so 15,491 `(work_id, normalized_title)` groups have >1 row. Reads use `DISTINCT`, so this is bloat, not wrong answers. `merge_candidate` similarly has 5 duplicate pairs.
6. **No metrics scraping or alerting.** `/metrics` is well-instrumented and correctly edge-404'd, but nothing consumes it. Silent Litestream replication failure would surface only at restore time. Two starter alerts are specified in the runbook.
7. **Covers DB has no size cap** (20.5 GB, deliberately unreplicated). AD-21's LRU cap is decided but unimplemented; first symptom of exhaustion would be `SQLITE_FULL` on the _replicated_ main DB.
8. **Writer-pool separation** evaluated and **recommended against** for now — 44 lock events in 32h is ~0.003%, `record_scan` already handles the hard `SQLITE_BUSY_SNAPSHOT` case correctly with `BEGIN IMMEDIATE` + full-transaction retry, and misclassifying a call site would silently reintroduce 517 with no retry. The cheaper next step is extending that retry pattern to the remaining multi-statement writers.

## Deploying

**Order matters: server first (or together), then reader/admin.** The admin's `mergeQueue` now expects a page envelope and both frontends send `includeNsfw`. There is a defensive unknown-field/unknown-argument strip-and-retry in `packages/api/src/graphql-backend.ts` covering the reader; the admin review panel has no such guard.

Budget **~35 s of extra startup** for migrations 0056–0059 (they run before the listener binds): 0058 ~26 s, 0059 ~5 s, the other two effectively instant.

Expect the review queue to grow from ~1,026 to roughly **10,400** as refused consolidation pairs are enqueued — correct behaviour (review beats irreversible deletion), bounded per boot, tunable via `CONSOLIDATE_MAX_BATCHES`.

Full sequence, verification curls and rollback are in `deploy/CLOUDFLARE-RUNBOOK.md`. Rollback caveat: if you revert the port binding to `0.0.0.0` you **must** also blank `TRUSTED_PROXY_CIDRS`, or XFF becomes forgeable.

## Two measurement lessons worth keeping

**Benchmark keys must be sampled randomly.** Two agents measured `chapter_owner_is_nsfw` and got
answers 240× apart. Sampling chapter uuids _in index order_ flatters the pre-existing plan by
~4000×. Migration 0058's header claimed a 351 ms → 0.72 ms win; re-measured against randomly
sampled keys, 0058 makes that query **worse** (169.65 → 178.83 ms) because it drops the planner's
skip-scan option. `known_chapter_id` degrades 59.81 → 122.93 ms. The real fix is 0062. **0058 and
0062 must deploy together — 0058 alone is a regression on the chapter-open request path.** The
correction is recorded in 0058's own header.

**A plausible diagnosis is not a root cause.** The frontend measured `latestChapterAt` returning
the query's own clock and concluded the server stamped `latest_chapter_at = now`. The server agent
checked the actual column: **0 of 13,802 rows are clock-derived**, 0 disagree with `MAX(upload_date)`.
The real cause was the display path — `latest_chapter_at` isn't in Suwayomi's wire shape, so a live
fetch yields `None`, `resolve_series_cached` discards the cached row on a stale-metadata read, and
`map_series` fell back to `last_fetched_at`, which our own fetch had just stamped to now. The fix
moved from the write path to the resolver.

probes with a `wget` that image doesn't ship). The audited compose was reapplied.

## Verified, not assumed

- **`/metrics` is not a deploy blocker.** Claimed to be exposed after rebuild; the running binary
  already serves it at 200 locally while the edge returns 404 — so the exclusion is edge-side and
  binary-independent.
- **mmap vs cgroup is safe.** SQLite maps the DB read-only; those pages are clean, reclaimable
  cache. The kernel evicts rather than OOM-kills. 6 GiB limit vs ~1.5 GiB anon has ample headroom.
- **`resolve_client_ip` is correct**, proven by packet-capturing the live tunnel: Cloudflare appends
  the true IP (leftmost really was spoofable), cloudflared adds no hop of its own (so rightmost is
  right for this topology), and a forged `CF-Connecting-IP` is rejected at the edge with 403.
